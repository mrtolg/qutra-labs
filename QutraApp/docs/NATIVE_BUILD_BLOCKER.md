# Native Windows build blocker — apostrophes in the project path

**Date:** 2026-07-27
**Status:** Root-caused and proven. Not an application defect. Workaround verified.
**RESOLVED 2026-08-11:** the working copy was relocated to an apostrophe-free ASCII
path (`C:\Dev\QutraLabs`). `cargo test` now compiles and passes from there
(59→70 tests over the redesign work). Develop from `C:\Dev\QutraLabs\QutraApp`;
the original `…\28''\…` checkout remains unbuildable by design and should be
retired.

`cargo test` / `cargo build` fail in this checkout. The previous audit recorded
this as a "Windows resource compiler failure in the context of special/Unicode
characters in the workspace path" and correctly warned it must not be
misclassified as an application-logic failure. This note closes that open
question with a precise cause, because "something about the path" is not
actionable.

**It is not Unicode. It is the two apostrophes in the directory name `28''`.**

## Symptom

```
error: failed to run custom build command for `contextos v0.1.0`
  thread 'main' panicked at tauri-winres-0.3.6/src/lib.rs:543:14:
  called `Result::unwrap()` on an `Err` value:
  Failed("RC.EXE failed to compile specified resource file")
```

## Root cause

`tauri-winres` generates `resource.rc` and embeds the icon path as an RC string
literal, escaping each apostrophe as `\'`:

```
32512 ICON "C:\\Users\\samil\\OneDrive\\Masaüstü\\28\'\'\\Qutra Labs\\src-tauri\\icons\\icon.ico"
```

`\'` is **not a valid escape sequence in the Windows Resource Compiler**. RC.EXE
recognises `\t`, `\n`, `\\`, `\"`, `\a` and octal `\ddd`; anything else is taken
literally. So RC.EXE looks for a directory literally named `28\'\'`, which does
not exist.

## Proof

Running RC.EXE directly on the generated file, and on the same file with only
the apostrophe escaping corrected:

```
A) as generated by tauri-winres
   resource.rc(27) : error RC2135 : file not found:
     C:\Users\samil\OneDrive\Masaüstü\28\'\'\Qutra Labs\src-tauri\icons\icon.ico
   exit 1

B) identical file, `28\'\'` replaced with `28''`
   exit 0   (compiles cleanly)
```

Variant B keeps the `ü` in `Masaüstü` and still succeeds — which rules out
Unicode and isolates the apostrophes as the sole trigger.

## The application code is fine

Built from a copy of this repository at an apostrophe-free path
(`C:\ctxos-build`), with no source changes:

```
running 37 tests
...
test result: ok. 37 passed; 0 failed; 0 ignored
```

That includes the four `consent::tests` added for the Private Lab boundary
(ADR 0007). There is no application defect behind this failure.

Note: a directory **junction** with an ASCII name does not work as a workaround.
Cargo canonicalises through it and reports the real path, so the same `\'`
escaping is emitted and RC.EXE fails identically.

## Fix options

1. **Rename or relocate the working copy** so the path contains no apostrophes —
   the cleanest fix; the trigger disappears at source. This is the user's
   directory, so it is their call to make.
2. **Build from an apostrophe-free copy/checkout** (what CI should do anyway;
   a clean checkout into a controlled workspace path never reproduces this).
3. Upstream: `tauri-winres` should not emit `\'`, since RC.EXE does not define
   it. Worth reporting, but it does not unblock this checkout today.

## Reproduce

```bash
cd src-tauri && cargo test --lib          # fails: RC.EXE
cat target/debug/build/contextos-*/out/resource.rc | grep ICON   # shows 28\'\'
```
